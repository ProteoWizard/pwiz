Osprey command-line usage

Osprey is a peptide-centric DIA search tool from the MacCoss lab. It reads DIA mass spectrometry data files (mzML, or vendor files where the vendor readers are installed) plus a spectral library and writes a BiblioSpecLite (.blib) library of FDR-controlled results that imports directly into Skyline. It runs as a standalone executable on Windows and Linux.

For the pipeline overview, per-stage detail, and how the four distributed HPC tasks split and join, see the workflow diagram: Osprey-workflow.html. The argument tables below are generated from the command-line declarations, so they always match the build; run Osprey --help for the same reference as text.

Osprey - Peptide-centric DIA analysis

USAGE: Osprey -i path/to/file ... -l path/to/file.blib|.tsv -o path/to/file.blib

Osprey -i path/to/file ... --fasta path/to/file.fasta -o path/to/file.blib

General I/O
ArgumentDescription
-i, --input path/to/file ...Mass spectrometry data files to search: mzML, or any format ProteoWizard reads, including vendor files (.raw, .d, .wiff, .lcd) where the vendor readers are installed
--input-list path/to/file.txtFile of input paths, one per line (# comments ignored). Bounded alternative to a long -i list.
-l, --library path/to/file.blib|.tsvSpectral library to search: a .blib (as --fasta and CarafeSharp write it, or one from Skyline or BiblioSpec), or, for comparing with DIA-NN, a library in the .tsv format DIA-NN imports, such as Java Carafe writes for it. Without --decoys-in-library, Osprey generates a reversed decoy for every target, and a library that holds decoys is refused. With --decoys-in-library, the library's own decoys are used: a .blib pairs them from its own table, and a .tsv marks them by its Decoy column or a decoy accession prefix and pairs them by --decoy-pairing-manifest (an FDRBench pairing manifest) or by composition.
-o, --output path/to/file.blibThe search result, for Skyline: a .blib that holds, for every precursor that passes FDR, the library spectrum it was searched with (the predicted one, with --fasta), the retention time and peak boundaries of its best run, its experiment-wide precursor q-value and PEP and its peptide q-value, and, for every run it was detected in, that run's retention time, peak boundaries and q-value. The protein groups its peptides belong to are in it too, with their q-values.
--work-dir path/to/folderWrite the intermediate files and the caches here instead of beside each input, so the data folder can be read-only. --output-dir and --cache-dir send one of the two elsewhere.
--output-dir path/to/folderWrite the intermediate files here - each run's scores and calibration and the analysis-wide FDR files - overriding --work-dir. The output and its reports stay where -o names.
--cache-dir path/to/folderWhere Osprey keeps the files it builds once and reuses in later searches: each run's .spectra.bin (its spectra, faster to read than the data file) and, for a .tsv library, the .blib it is converted to (e.g. hela.tsv.blib). By default each goes beside the file it comes from, or under --output-dir or --work-dir when that folder is read-only. Give it to put them elsewhere, for example when the data and the library are on a read-only share, or to let several analyses share one cache. An HPC run (--task) that writes to an --output-dir away from the data should give every node the same one.
--export-library path/to/file.blibWrite the library given by --library to this path as a .blib and exit without searching. It is the file a search keeps in its cache for a .tsv library (e.g. hela.tsv.blib): the library as a search loads it, with its decoys and their pairing in its own table (with --decoys-in-library, and --decoy-pairing-manifest for a .tsv), so it needs no manifest, searches back exactly as the original did, and Skyline can import it.
Library Build
ArgumentDescription
--fasta path/to/file.fastaPredict the spectral library from this protein FASTA with CarafeSharp's models and search it, in place of -l. The library is written beside the output as <output>.predicted.blib and can be given to -l next time; its working files go in <output>.predicted/. The options of the Library Digest and Library Prediction sections apply, and with --training-input those of Library Tuning.
--training-input path/to/file ...With --fasta: tune the models on these runs before the library is predicted. The runs are searched with a library predicted as it is without this option, their training exports tune the MS2 and RT models, and the library the output is searched with is predicted with the tuned models. A run need not be one of -i: one that is not is searched for the tuning only and is absent from the output. The tuned model is saved beside the output as <output>.model.zip, which --model takes next time. The options of the Library Tuning section apply.
--training-input-list path/to/file.txtWith --fasta: a file of --training-input runs, one path per line (# comments ignored), as --input-list is for -i: a long list of runs on the command line can pass the Windows command-line limit and hides the other arguments.
--model path/to/file.model.zipWith --fasta: predict the library with this saved fine-tuned model (.model.zip, from CarafeSharp's training) instead of the pretrained models. With --training-input, the tuning starts from it.
--device <auto | gpu | cpu>With --fasta: where the library is predicted, auto (default: the GPU when this computer has an NVIDIA GPU that can use the CUDA runtime and the runtime is installed, see --install-cuda-runtime, else the CPU), gpu (the GPU; a run that cannot use it fails before it starts, saying why) or cpu. The log names the device every library phase ran on.
--torch-runtimes path/to/folderThe folder of installed libtorch runtimes, where --install-cuda-runtime installs the NVIDIA CUDA runtime and --device looks for it, each runtime in a folder of its own (default: Osprey\torch under the user's local application data folder). Skyline passes its Tools folder, so one download serves its AlphaPeptDeep and Osprey; a cluster job names a shared folder.
--install-cuda-runtimeDownload the NVIDIA CUDA runtime from nuget.org (several GB; the size is logged first, and every package is checked against the hashes this build was tested with) into the --torch-runtimes folder and exit, so that --device can predict on the GPU. Needs nothing else on the command line.
--entrapment [<ratio>]With --fasta: add an entrapment peptide to every target (or to this fraction of the targets, 0.1 to 1), shuffled from the target or, with --entrapment-fasta, drawn from a foreign proteome, each with a decoy of its own. For measuring the true FDR with FDRBench, whose pairing manifest is written as <output>.predicted/pairing.tsv.
--entrapment-fasta path/to/file.fastaWith --entrapment: draw the entrapment peptides, matched in mass, from this foreign-species protein FASTA instead of shuffling the targets.

Scoring & Tolerance
ArgumentDescription
--resolution <hram | unit>How spectra are scored: hram (the default; Orbitrap, Astral and TOF instruments) bins them finely, uses the MS1 precursor features, and matches fragments and precursors within 10 ppm; unit (ion traps such as Stellar) bins them coarsely, without MS1 features, and matches fragments within 0.5 m/z and precursors within 1.0 m/z. The resolution is not detected from the data: a search of unit-resolution data must give unit.
--fragment-tolerance <number>The fragment m/z tolerance, in the unit --fragment-unit names (default: 10 ppm, or 0.5 m/z with --resolution unit).
--fragment-unit <ppm | mz>The unit of --fragment-tolerance: ppm or mz (default: ppm, or mz with --resolution unit).
--no-prefilterScore every library precursor in each isolation window, not only those whose fragments first show a coelution signal. About 30% slower; for checking that the pre-filter loses no detections.
--demux <off | auto>Demultiplex overlapping-window (staggered) DIA to its narrow bins before searching (default: off)
--centroid <vendor | centrix>Who centroids profile spectra: the vendor library, or Centrix, a lasso centroider for ion trap (unit resolution) profile data that separates peaks closer than 1 Th. Centrix reads the profile even from a vendor file, and its spectra are cached apart from the vendor-centroided ones (default: vendor)
--centrix-sigma-ms1 <Th>With --centroid centrix: the MS1 profile peak sigma in Th (default: 1.1 point spacings on a linear ion trap, otherwise one species' peak width measured from the run)
--centrix-sigma-ms2 <Th>With --centroid centrix: the MS2 profile peak sigma in Th (default: 1.1 point spacings on a linear ion trap, otherwise one species' peak width measured from the run)
--centrix-solver <descent | active-set>With --centroid centrix: how each region of a spectrum is fitted. descent: Centrix's own coordinate descent; active-set: the exact optimum of the same fit, several times faster (default: descent)
FDR & Protein Inference
ArgumentDescription
--run-fdr <threshold>The run-level FDR threshold (default: 0.01). A reported precursor gets an identification in Skyline in each run where its q-value in that run is at most this, or in its best run when it is in none; the scoring model is also trained and tested at it.
--experiment-fdr <threshold>The experiment-level FDR threshold (default: 0.01): a precursor is reported when its q-value across all the runs is at most this. --fdr-level says which q-value.
--reconciliation-compaction-fdr <threshold>Peptide q-value threshold for keeping first-pass peptides for cross-run reconciliation and the second pass (default: 0.01 = --run-fdr; loosen e.g. to 0.05 to broaden the reconciliation pool)
--protein-fdr <threshold>Protein-level FDR threshold (default: 0.01)
--fdr-level <precursor | peptide | both>Which experiment-level q-value --experiment-fdr applies to: precursor (the default; each precursor's own), peptide (its peptide's, over all its charge states), or both (the larger of the two).
--shared-peptides <all | razor | unique>How a peptide shared by several protein groups counts in protein inference: all (the default; toward every group it maps to), razor (toward only the group with the most unique peptides), or unique (toward none).
--fdrbench path/to/file.tsvWrite an FDRBench-compatible input TSV to this path. The level is taken from --fdr-level (peptide; precursor and both emit precursor-level). Includes every reported target, i.e. the peptides actually written to the output, regardless of q-value, with the raw SVM discriminant as 'score', so FDRBench can compute true FDR via entrapment counting without truncation at Osprey's threshold.
--fdrbench-per-runWith --fdrbench: emit one row per (precursor, run) using run-level q-values (adds a 'run' column). Default is one row per precursor using experiment-level q-values.
--fdrbench-pass <1 | 2 | both>With --fdrbench: which FDR pass to emit. 2 (default) = the second-pass results written to the blib (the FDR of what Osprey reports). 1 = the full first-pass pool, before it is filtered for the second pass (every scored target, regardless of q), with first-pass q-values, matching the FDRBench input of the original Rust Osprey (the assumption the second-pass output rests on). both = emit both in one run, writing the --fdrbench path with .pass1 / .pass2 stem suffixes.

Distributed / HPC

--fasta runs as one process, or task by task: --task PredictTrainingLibrary; the four search stages with --training-search; --task TrainModel; --task PredictLibrary; then the four search stages. Every node takes the same command line and its own --task, and each task reads only what the tasks before it wrote.

ArgumentDescription
--task <SpectraCache | PredictTrainingLibrary | TrainModel | PredictLibrary | PerFileScoring | FirstPassFDR | PerFileRescoring | SecondPassFDR | TrainingExport | ModelDiagnostics>HPC: run exactly one task (one node = one task). Omit for the full pipeline. SpectraCache stages the .spectra.bin caches; TrainingExport writes the --training-export parquets, and on a COMPLETED run only the missing ones; ModelDiagnostics regenerates only the --model-diagnostics report for a COMPLETED run, writing no other output. With --fasta, PredictTrainingLibrary, TrainModel and PredictLibrary run the library build one phase at a time, and the four search stages search the library it predicts, or with --training-search the tuning runs.
--training-searchWith --fasta and --training-input: the stage --task selects is a stage of the tuning runs' search, not the output's: it searches the --training-input runs with the library PredictTrainingLibrary predicts, writes into <output>.predicted/training/, and writes the training exports TrainModel reads. Give it to every node of that search and the same command line without it to the others. The same four tasks for any number of tuning runs, one included.
--task-filesWith --task: print the files the task reads and writes for this command line, one per line as input or output, the task and the path, and exit without running it: what a node must be given and what it hands on.

Distributed execution (HPC)

Run with no --task for the whole pipeline in one process. For distributed (HPC / workflow-engine) execution the pipeline splits at its join / fan-out boundaries into four single-task workers - one node = one --task: PerFileScoring (split, per file) → FirstPassFDR (join, all files) → PerFileRescoring (split, per file) → SecondPassFDR (join, all files). Pass the same --library and search options to every task; the parquet integrity check rejects inputs whose search/library hash does not match.

# split 1 - one process per mzML (writes <stem>.scores.parquet, <stem>.calibration.json beside each input)
Osprey --task PerFileScoring -i s1.mzML -l hela.tsv -o out.blib --resolution unit --protein-fdr 0.01

# join 1 - one process over ALL runs (pass a sorted list so the order is deterministic)
Osprey --task FirstPassFDR --input-list runs.txt -l hela.tsv -o out.blib --resolution unit --protein-fdr 0.01
#   writes beside each parquet: <stem>.1st-pass.fdr_scores.bin; and once for the analysis: out.1st-pass.*

# split 2 - one process per file (the scores parquet and its intermediate files together)
Osprey --task PerFileRescoring -i s1.mzML -l hela.tsv -o out.blib --resolution unit --protein-fdr 0.01
#   writes: <stem>.scores-reconciled.parquet, and <stem>.training.parquet with --training-export

# join 2 - one process over ALL runs, reading their reconciled parquets (writes out.blib)
Osprey --task SecondPassFDR --input-list runs.txt -l hela.tsv -o out.blib --resolution unit --protein-fdr 0.01

EVERY task takes -i, naming the DATA files - the same names the first split was given. A join task derives the parquet and intermediate files of each run from the input stem, so the data file itself need not still exist: what has to be in the working directory of the worker (or under --output-dir) is the artifacts of that run. FirstPassFDR reconciliation is order-sensitive, so pass a deterministically sorted list - --input-list takes one path per line and is what a cohort past a few hundred runs needs, since -i spends the command line at O(files). Let the scheduler do the fan-out (one file per split process) rather than --parallel-files, which is the single-node multi-file mode.
