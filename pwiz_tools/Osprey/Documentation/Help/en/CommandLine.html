Osprey command-line usage

Osprey is a peptide-centric DIA search tool from the MacCoss lab. It reads DIA mzML files plus a spectral library and writes a BiblioSpecLite (.blib) library of FDR-controlled results that imports directly into Skyline. It runs as a standalone executable on Windows and Linux.

For the pipeline overview, per-stage detail, and how the four distributed HPC tasks split and join, see the workflow diagram: Osprey-workflow.html. The argument tables below are generated from the command-line declarations, so they always match the build; run Osprey --help for the same reference as text.

Osprey - Peptide-centric DIA analysis

USAGE: osprey -i <file1.mzML> [file2.mzML ...] -l <library.tsv> -o <output.blib>

osprey -i <file1.mzML> [file2.mzML ...] --fasta <proteome.fasta> -o <output.blib>

Library Build
ArgumentDescription
--fasta <proteome.fasta>Predict the spectral library from this protein FASTA with CarafeSharp's models and search it, in place of -l. The library is written beside the output as <output>.library.blib and can be given to -l next time; its working files go in <output>.library/. The options of the Library Digest and Library Prediction sections apply, and with --training-input those of Library Tuning.
--training-input <file1.mzML ...>With --fasta: tune the models on these runs before the library is predicted. The runs are searched with a library predicted as it is without this option, their training exports tune the MS2 and RT models, and the library the output is searched with is predicted with the tuned models. A run need not be one of -i: one that is not is searched for the tuning only and is absent from the output. The tuned model is saved beside the output as <output>.carafemodel, which --model takes next time. The options of the Library Tuning section apply.
--model <file.carafemodel>With --fasta: predict the library with this saved fine-tuned model (.carafemodel, from CarafeSharp's training) instead of the pretrained models. With --training-input, the tuning starts from it.
--device <gpu | cpu>With --fasta: where the library is predicted, gpu (falling back to the CPU with a warning when no CUDA runtime is present) or cpu (default: gpu).
--entrapment [<ratio>]With --fasta: add an entrapment peptide to every target (or to this fraction of the targets, 0.1 to 1), shuffled from the target or, with --entrapment-fasta, drawn from a foreign proteome, each with a decoy of its own. For measuring the true FDR with FDRBench, whose pairing manifest is written as <output>.library/pairing.tsv.
--entrapment-fasta <foreign.fasta>With --entrapment: draw the entrapment peptides, matched in mass, from this foreign-species protein FASTA instead of shuffling the targets.

EXAMPLES:

osprey -i sample.mzML -l library.tsv -o results.blib

osprey -i *.mzML -l library.tsv -o results.blib --resolution hram

osprey -i *.mzML --fastahuman.fasta -o results.blib --resolution hram

HPC SPLIT (one node = one --task): see --task above.

OTHER FORMS ACCEPTED: a value may also be joined to its option (--output=results.blib), and a file that exists may be given without -i. The library build options are listed in the standard form (--miss-c 1) and, for compatibility with Java Carafe's command lines, also accepted with its underscores (--miss_c 1).

Distributed execution (HPC)

Run with no --task for the whole pipeline in one process. For distributed (HPC / workflow-engine) execution the pipeline splits at its join / fan-out boundaries into four single-task workers - one node = one --task: PerFileScoring (split, per file) → FirstPassFDR (join, all files) → PerFileRescoring (split, per file) → SecondPassFDR (join, all files). Pass the same --library and search options to every task; the parquet integrity check rejects inputs whose search/library hash does not match.

# split 1 - one process per mzML (writes <stem>.scores.parquet, <stem>.calibration.json beside each input)
Osprey --task PerFileScoring -i s1.mzML -l hela.tsv -o out.blib --resolution unit --protein-fdr 0.01

# join 1 - one process over ALL runs (pass a sorted list so the order is deterministic)
Osprey --task FirstPassFDR --input-list runs.txt -l hela.tsv -o out.blib --resolution unit --protein-fdr 0.01
#   writes beside each parquet: <stem>.1st-pass.fdr_scores.bin; and once for the analysis: out.1st-pass.*

# split 2 - one process per file (the scores parquet and its intermediate files together)
Osprey --task PerFileRescoring -i s1.mzML -l hela.tsv -o out.blib --resolution unit --protein-fdr 0.01
#   writes: <stem>.scores-reconciled.parquet, and <stem>.training.parquet with --training-export

# join 2 - one process over ALL runs, reading their reconciled parquets (writes out.blib)
Osprey --task SecondPassFDR --input-list runs.txt -l hela.tsv -o out.blib --resolution unit --protein-fdr 0.01

EVERY task takes -i, naming the DATA files - the same names the first split was given. A join task derives the parquet and intermediate files of each run from the input stem, so the data file itself need not still exist: what has to be in the working directory of the worker (or under --output-dir) is the artifacts of that run. FirstPassFDR reconciliation is order-sensitive, so pass a deterministically sorted list - --input-list takes one path per line and is what a cohort past a few hundred runs needs, since -i spends the command line at O(files). Let the scheduler do the fan-out (one file per split process) rather than --parallel-files, which is the single-node multi-file mode.
